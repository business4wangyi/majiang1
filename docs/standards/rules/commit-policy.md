# 版本提交判定规范

> **E0 强制执行** — 提交前 MUST Read。与具体 Git 客户端无关；命令细则见 [git-mcp-automation.md](git-mcp-automation.md)。

## 必须满足（AND）

1. **功能完整**：用户请求的功能已完整实现（或用户明确要求阶段性保存）
2. **代码质量**：无明显语法/逻辑错误，符合 `development.md` 与相关测试约定
3. **变更规模**：建议 1–10 个文件、约 10–500 行、关联性强；更大变更须拆提交或经用户确认
4. **用户态度**：用户未明确拒绝提交；**默认不主动 commit**，除非用户要求或本仓自动化任务合同明确授权

## 允许提交

- 新功能 / Bug 修复 / 重构完成
- 配置、文档、测试补充完成
- 用户明确要求「提交 / commit」
- 阶段性完成并希望保存进度

## 禁止提交

- 实验性/临时代码、未清理的调试代码
- 功能不完整或已知明显缺陷
- 用户明确「不要提交 / 先不 commit」
- 含密钥、Token、证书等敏感明文（见 `security-baseline.md`）

## 提交消息格式

```text
type(scope): 中文主题

正文（可选，中文完整句，说明动机与影响）
```

### 语言（强制）

- **主题与正文必须使用中文**（路径、API 名、专有名词可保留英文）
- `type` / `scope` 可英文；禁止整段主题仅用英文

| type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档 |
| `style` | 格式 |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建/工具 |

**推荐**：`docs(standards): 落地规则触发表与定封顶流程`  
**不推荐**：`docs(standards): add rules index`

## 与自动化的关系

- 自动提交仍须满足本文件 + `git-mcp-automation.md`
- 破坏性 Git 命令（`reset --hard`、`clean -fd`、force push 等）须用户显式确认
