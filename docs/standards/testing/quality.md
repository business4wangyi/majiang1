# 测试与质量保障规范

> **适用范围**：本仓库所有游戏模块、训练/评估脚本、UI/CLI 适配层与文档驱动的验收工作。  
> **规范定位**：作为 `docs/standards/` 下的共享测试质量正文，供 AGENTS、Cursor、Codex 等 IDE 入口引读。  
> **项目依据**：当前测试入口为 `npm test`，由 `scripts/test/run-mocha-cjs.js` 装载 `tests/**/*.test.ts`，测试栈以 Mocha + Chai + Sinon + ts-node 为主。

## 1. 测试分层

### 1.1 单元测试

适用对象：

- `src/<game>/core/` 中的纯规则、状态机、计分、牌/棋子管理。
- `src/<game>/strategy/` 中不依赖长时间训练和外部模型下载的确定性策略函数。
- `src/<game>/tools/` 中的日志、时间、性能统计等纯工具。

要求：

- 优先使用确定性输入构造断言，避免依赖随机默认状态。
- 对麻将胡牌条件、计分和规则引擎必须覆盖正例、反例、边界牌型。
- 测试名称应表达业务含义；麻将牌型测试可使用中文描述以保持可读性。

### 1.2 集成测试

适用对象：

- `core + ui` 的对局流程，例如摸牌、出牌、切换玩家、结算。
- `core + strategy` 的 AI 对局或动作选择适配。
- 解析器、模型加载、外部文件读取等跨模块行为。

要求：

- 集成测试必须明确被测边界，不把长时间训练混入默认回归。
- 涉及控制台输出时应 stub 或捕获输出，避免污染测试日志。
- 涉及单例或全局状态时必须在 `beforeEach` / `afterEach` 中重置。

### 1.3 回归测试

默认回归入口：

```bash
npm test
```

当前含义：

- 通过 `scripts/test/run-mocha-cjs.js` 执行 `tests/**/*.test.ts`。
- 覆盖麻将核心规则、胡牌牌型、UI 输入、日志，以及黑白棋 Edax 解析相关回归。
- 脚本会拦截测试中的 `process.exit(0)`，防止被测代码提前吞掉测试进程。

每日回归入口：

```bash
npm run regression:daily
```

当前含义：

- 由 `scripts/test/daily-regression-report.js` 生成 `logs/daily-regression-report.md`。
- 默认纳入 `npm test`，暂不强制纳入 `npm run build`。
- 若后续修复既有 TypeScript 编译问题，可将 `npm run build` 升级为每日回归硬门槛。

## 2. 测试目录与命名

### 2.1 目录规则

- 测试文件放在 `tests/<game>/` 下，与 `src/<game>/` 模块对应。
- 麻将胡牌条件测试放在 `tests/majiang/win-conditions/`。
- 共享测试构造器放在对应游戏目录下，例如 `tests/majiang/test-utils.ts`。
- 不在 `src/` 中混放测试文件，除非该目录本身是示例或演示代码且不进入默认回归。

### 2.2 命名规则

- 测试文件使用 `*.test.ts`，确保被默认回归入口发现。
- 规则/牌型测试文件应与实现文件保持可追踪命名，例如：
  - 实现：`src/majiang/core/win-conditions/win-conditions_one-voided-suit.ts`
  - 测试：`tests/majiang/win-conditions/win-conditions_one-voided-suit.test.ts`
- 修复历史缺陷时可保留专门回归文件，但文件名应表达修复对象，不使用临时命名。

## 3. 断言质量

### 3.1 必须断言业务结果

测试应优先断言业务可观察结果：

- 游戏状态：当前玩家、玩家状态、对局状态、牌山数量。
- 牌/棋子变化：手牌数量、弃牌、明牌、副露。
- 规则结果：是否可胡、是否可吃碰杠、得分结果、错误分支。
- 输出行为：必要时断言提示文本或日志调用，但不以日志替代核心断言。

### 3.2 禁止低价值断言

避免以下测试形态：

- 只断言对象“存在”，但不验证关键字段。
- 复制实现逻辑后再与实现结果比较。
- 用快照替代麻将规则、计分、状态流的精确断言。
- 为了让测试通过而放宽断言到无意义范围。

### 3.3 边界与异常

新增规则或修复 bug 时至少考虑：

- 正常路径：符合规则时返回预期结果。
- 反向路径：不符合规则时明确返回 false、空数组或受控错误。
- 边界路径：空手牌、重复牌、牌数异常、牌山为空、游戏已结束。
- 恢复路径：非法输入后状态不应被部分修改。

## 4. 随机性、时间与外部依赖

### 4.1 随机性

- 默认回归测试必须可重复。
- 涉及洗牌、AI 随机决策、训练采样时，应固定输入、注入随机源或断言不依赖具体顺序的性质。
- 不允许用“多跑几次大概率通过”作为默认测试策略。

### 4.2 时间与倒计时

- 倒计时、延迟、定时器测试应使用 fake timer 或可注入时钟。
- 默认测试不应真实等待长时间倒计时。
- 测试完成后必须清理 timer、listener、stub、mock。

### 4.3 外部依赖

- 默认 `npm test` 不应依赖网络、密钥、远端服务或本地大型模型下载。
- 需要外部二进制或模型的测试应提供显式开关，并在缺失依赖时给出清晰跳过或失败原因。
- 训练任务、长时间 benchmark、模型生成不进入默认回归；如需验证，应提供独立脚本和成本说明。

## 5. UI / CLI 测试

### 5.1 CLI

- CLI 测试应保护既有用户路径，不因 Web UI 改造改变命令行交互。
- 控制台输出应通过 stub 捕获，避免污染测试输出。
- 输入解析测试应覆盖合法输入、非法输入、取消/超时、边界编号。

### 5.2 Web UI

当前 Web UI 仍处于设计/落地阶段，测试策略应随实现分阶段补齐：

- 视图模型测试：验证后端/核心状态到 UI 只读模型的映射。
- 组件测试：验证 Lobby、Table、ResultModal 的关键状态展示与操作禁用。
- 交互测试：验证等待 AI、可出牌、可响应、错误、结算等状态转换。
- 诊断测试：验证错误上下文、事件流、状态快照可被展示或导出。

Web UI 测试不得在前端重写麻将规则判断；可用动作与结算结果应来自核心层或适配层输出。

## 6. 质量门槛

### 6.1 开发完成前

以下场景必须补充或更新测试：

- 修改 `src/<game>/core/` 规则、状态、计分、牌/棋子管理。
- 修复已复现 bug。
- 新增 UI 状态、输入路径、错误处理或诊断出口。
- 修改默认回归入口、测试脚本或测试目录结构。

### 6.2 提交前

推荐执行：

```bash
npm test
```

若改动涉及 TypeScript 类型、跨模块导出、构建脚本，建议额外执行：

```bash
npm run build
```

说明：

- 当前每日回归脚本已记录 `npm run build` 仍存在既有风险，不作为默认硬门槛。
- 若构建失败来自既有问题，提交说明中应明确“未修复的既有失败”与本次改动关系。

## 7. 文档与验收

- 需求、设计或 UI 交互文档新增验收矩阵时，应同步考虑是否需要测试用例或手工验收清单。
- 文档中的验收点应可追踪到测试、脚本、人工验证步骤或后续 TODO。
- 测试报告、每日回归报告、门禁报告属于过程产物；若写入仓库，应说明生成方式和适用范围。

## 8. 与现有规范的关系

- 依据 `docs/standards/rules/development.md`：测试应服务模块分层，避免将核心规则搬入 UI 或测试辅助层。
- 依据 `docs/majiang/FOLDER_STRUCTURE.md`：麻将核心规则优先覆盖 `core/`，UI 测试只验证渲染与交互编排。
- 依据 `docs/standards/rules/desktop-commander-mcp-priority.md`：长时间训练、编译、测试任务优先使用具备会话管理能力的工具；当前环境不支持时需说明替代方案。
- 当前未发现规范冲突；若测试便利性与核心分层冲突，应优先维护核心分层边界。
