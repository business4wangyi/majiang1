# 架构重构提案

> **创建日期**: 2025-11-21  
> **状态**: 提案中

## 📋 问题分析

### 问题1: 游戏模块组织方式

**当前结构**：
```
src/
├── majiang/
├── tic-tac-toe/
├── othello/
├── ai/
├── ai-assistant/
├── shared/
└── utils/
```

**问题**：
- 三个游戏模块与AI框架、工具模块平级，缺乏层次感
- 新开发者可能不清楚哪些是游戏，哪些是框架

**建议**：
```
src/
├── games/              # 游戏模块统一目录
│   ├── majiang/
│   ├── tic-tac-toe/
│   └── othello/
├── ai/                 # AI框架（保留）
├── ai-assistant/       # AI助手（待评估）
├── shared/             # 共享代码（待评估）
└── utils/              # 工具函数（待评估）
```

**优点**：
- ✅ 清晰的层次结构
- ✅ 游戏模块集中管理
- ✅ 便于扩展新游戏

**缺点**：
- ⚠️ 需要更新所有导入路径
- ⚠️ 可能影响现有脚本和文档

### 问题4: AI组件复用

**当前情况**：
- 每个游戏都实现了自己的AI组件（AlphaZero、MCTS、DQN等）
- 可能存在大量重复代码

**分析要点**：
1. 哪些AI组件可以抽象为通用组件？
2. 哪些组件是游戏特定的？
3. 如何设计通用的AI框架？

**建议**：
- 创建通用的AI框架模块
- 游戏特定的部分保留在各自的 `strategy/` 目录
- 通用部分提取到 `src/ai/` 或新的 `src/ai/common/` 目录

## 🔍 详细分析

### ai/ 目录分析

**当前状态**：
- 目录结构：`src/ai/framework/` 和 `src/ai/utils/`
- **问题**：目录存在但内容为空或未使用
- **结论**：可能是预留的目录，目前未被使用

**建议**：
- 如果确实未使用，可以考虑删除或作为未来通用AI框架的存放位置
- 如果计划使用，应该明确其职责和内容

### ai-assistant/ 目录分析

**当前状态**：
- **主要功能**：AI助手框架，提供视觉识别、策略分析、自动执行等功能
- **当前实现**：仅实现了 tic-tac-toe 的AI助手
- **核心模块**：
  - `vision-recognition.ts`: 视觉识别（屏幕/摄像头）
  - `output-controller.ts`: 输出控制（自动执行、建议显示、语音）
  - `strategy-simplifier.ts`: 策略简化规则
  - `tic-tac-toe/`: 井字棋具体实现

**与 ai/ 的关系**：
- `ai-assistant/` 是应用层框架，用于构建AI辅助工具
- `ai/` 目前为空，可能是底层AI算法框架
- **结论**：两者职责不同，不应合并

**建议**：
- 保留 `ai-assistant/` 作为AI助手框架
- 如果 `ai/` 未使用，可以删除或明确其用途

### shared/ 目录分析

**当前状态**：
- **内容**：仅有一个 `types.ts` 文件
- **功能**：共享类型定义（主要用于MVP工具和AI助手框架之间的类型统一）
- **使用情况**：目前主要针对 tic-tac-toe 的类型定义

**与 utils/ 的区别**：
- `shared/`: 类型定义和数据结构（类型层面）
- `utils/`: 工具函数和实用程序（功能层面）

**建议**：
- 如果 `shared/` 只包含类型定义，可以考虑：
  1. 保留但扩展为通用的共享类型库
  2. 或者合并到 `utils/` 中（如果类型定义不多）

### utils/ 目录分析

**当前状态**：
- **内容**：仅有一个 `tfjs-compat-fix.ts` 文件
- **功能**：TensorFlow.js兼容性修复（修复Node.js中util.isNullOrUndefined不存在的问题）
- **使用情况**：被多个使用TensorFlow.js的模块导入

**与 shared/ 的区别**：
- `utils/`: 工具函数（功能实现）
- `shared/`: 类型定义（类型声明）

**建议**：
- 两者职责不同，但内容都很少
- 可以考虑合并为 `common/` 或 `shared/`，包含类型和工具函数

### AI组件重复分析

**分析结果**：

1. **AlphaZero 实现**：
   - **othello**: `strategy/networks/alphazero-network.ts` + `strategy/mcts/alphazero-mcts.ts`
   - **majiang**: `strategy/ai-alphazero/majiang-alphazero-network.ts` + 内嵌MCTS
   - **重复度**：⭐⭐⭐ (中等)
   - **问题**：
     - 两者都实现了AlphaZero的核心算法（神经网络 + MCTS）
     - 但游戏特定的部分（状态编码、动作解码）不同
   - **建议**：
     - 提取通用的AlphaZero框架（网络架构、MCTS算法）
     - 游戏特定的部分（状态编码器、动作解码器）保留在各游戏中
     - 通过适配器模式连接通用框架和游戏特定部分

2. **MCTS 实现**：
   - **othello**: `strategy/mcts/alphazero-mcts.ts` (独立实现)
   - **majiang**: 内嵌在 `majiang-alphazero-agent.ts` 中
   - **重复度**：⭐⭐⭐⭐ (高)
   - **问题**：MCTS算法本身是通用的，不应该重复实现
   - **建议**：
     - 提取通用的MCTS实现到 `src/ai/common/mcts/`
     - 各游戏通过配置和适配器使用通用MCTS

3. **DQN 实现**：
   - **othello**: `strategy/networks/dqn-network.ts` (完整实现)
   - **其他游戏**：未实现
   - **重复度**：⭐ (低，目前只有othello实现)
   - **建议**：
     - 如果其他游戏也需要DQN，应该提取为通用实现
     - 目前可以保留在othello中，但设计时考虑通用性

4. **训练器**：
   - **othello**: `strategy/trainers/alphazero-trainer.ts`
   - **majiang**: `strategy/ai-alphazero/self-play-trainer.ts` 等
   - **重复度**：⭐⭐⭐ (中等)
   - **问题**：训练循环的模式相似，但游戏特定的部分不同
   - **建议**：
     - 提取通用的训练框架（训练循环、经验回放、模型保存等）
     - 游戏特定的部分（游戏环境、状态转换）通过接口注入

**总结**：
- **高重复度**：MCTS算法（应该提取）
- **中重复度**：AlphaZero框架、训练器（可以部分提取）
- **低重复度**：游戏特定的状态编码、动作解码（应该保留在各游戏中）

## 📝 重构建议

### 方案A: 渐进式重构（推荐）⭐

**步骤1**: 合并 shared 和 utils ✅ **优先**
- **原因**：两者内容都很少，职责相关
- **操作**：
  - 将 `utils/tfjs-compat-fix.ts` 移到 `shared/utils/`
  - 将 `shared/types.ts` 保留在 `shared/types/`
  - 统一为 `src/shared/` 目录
  - 更新所有导入路径

**步骤2**: 清理或明确 ai/ 目录
- **操作**：
  - 如果 `ai/` 目录为空或未使用，删除它
  - 或者明确其用途，作为通用AI框架的存放位置

**步骤3**: 提取通用MCTS实现 ⭐ **高优先级**
- **原因**：MCTS算法是通用的，不应该重复实现
- **操作**：
  - 创建 `src/ai/common/mcts/` 目录
  - 提取通用的MCTS算法（基于othello的实现，因为它更完整）
  - 创建游戏适配器接口
  - 各游戏通过适配器使用通用MCTS

**步骤4**: 提取通用AlphaZero框架 ⭐ **中优先级**
- **原因**：AlphaZero的核心框架是通用的
- **操作**：
  - 创建 `src/ai/common/alphazero/` 目录
  - 提取通用的网络架构、训练循环
  - 游戏特定的部分（状态编码、动作解码）保留在各游戏中
  - 通过适配器模式连接

**步骤5**: 重组游戏目录（可选）⚠️ **低优先级**
- **原因**：影响面大，收益相对较小
- **操作**：
  - 将游戏移到 `src/games/` 目录
  - 更新所有导入路径
  - 更新文档和脚本

### 方案B: 激进式重构

**一次性完成所有重构**：
- 优点：架构清晰，一步到位
- 缺点：风险高，影响面大

## 🎯 推荐方案

**推荐采用方案A（渐进式重构）**，原因：
1. 风险可控，可以逐步验证
2. 不影响现有功能
3. 可以分阶段提交和测试
