# 麻将 Web UI 产品交互设计补充文档

> **文档定位**：补充麻将 Web UI 的产品级交互与视觉设计要求。  
> **适用阶段**：MVP 后续 UI/UX 质量提升、前端实现拆分、验收用例补齐。  
> **不替代内容**：不重写麻将核心规则，不改变 CLI 交互，不替代 `src/majiang/core/` 与 `src/majiang/strategy/` 的业务实现。  
> **规范依据**：`AGENTS.md`、`docs/standards/rules/development.md`、`docs/majiang/FOLDER_STRUCTURE.md`。

> **当前状态**：冲顶进行中（B1/B2/B3 已解除）  
> **阻塞项**：无

## 1. 背景与目标

现有麻将 Web UI 设计材料已经能约束 MVP 技术落地：保留核心规则、保护 CLI 路径、跑通 Lobby / Table / ResultModal。但它更偏技术设计与验收矩阵，缺少足够细的产品交互说明，无法指导“好用、好看、能看懂局势”的 UI 改版。

本补充文档的目标是把 Web UI 从“可运行”推进到“可理解、可操作、可复盘”：

- 用户能在 3 秒内看懂当前轮到谁、自己能做什么、为什么能做。
- 用户能在 1 局内形成稳定空间记忆：自己手牌在底部，其他玩家围绕牌桌，牌河与动作流清晰可追踪。
- 用户能在关键节点获得明确反馈：等待 AI、可出牌、可响应、错误、忙碌、结束结算。
- 开发者能通过诊断/复盘入口确认前端展示与后端状态是否一致。
- Web UI 只做表现与交互编排，规则判断仍来自 `src/majiang/core/`，AI 决策仍来自 `src/majiang/strategy/`，符合 `docs/majiang/FOLDER_STRUCTURE.md` 的 UI 层薄原则。

### 1.1 两阶段闭环（先设计冻结，再开发验收）

为消除“先设计却要求实现截图”的流程矛盾，本项目统一采用两阶段闭环：

- **阶段A：设计冻结验收（无代码实现）**
  - 可接受证据：Figma/Pencil、线框图、高保真图、交互流图、状态图。
  - 禁止要求：实现截图、DOM 节点证据、运行态脚本结果、录屏中的真实交互执行证据。
  - 通过门槛：桌心主路径、牌面系统、四方座位、移动端策略、结果页信息结构达到可实现且可审核的一致设计标准。
- **阶段B：实现一致性验收（有代码实现）**
  - 必交证据：桌面与移动端截图、关键交互录屏、`tsumo/ron/draw/abort` 四类结果页证据、必要 DOM/状态校验。
  - 校验目标：实现必须与阶段A冻结稿一致，不得偏离核心视觉与交互口径。

### 1.2 阶段切换闸门

- 只有阶段A审核通过，才进入阶段B开发。
- 阶段B若发现设计缺口或解释不闭环，必须回流阶段A补冻结，再继续实现。
- 本文统一术语：**`冲顶审核`** 为主叫法；“顶级档”仅作括注说明，不单独作为流程名词。

## 2. 产品体验原则

### 2.1 信息层级

1. **主任务优先**：当前玩家、当前动作、可操作按钮、自己手牌永远位于最高层级。
2. **局势可读**：最近动作、弃牌来源、响应原因、分数变化必须可见，不依赖用户猜。
3. **细节渐进展示**：默认只显示必要信息；完整日志、规则判定、AI 思考细节放入诊断抽屉。
4. **避免规则重写**：所有“能否吃/碰/杠/胡/出牌”的可用性由后端/核心状态提供，前端不得自行推导替代。
5. **CLI 不受影响**：Web UI 新增状态、动效、诊断入口不得改动现有 CLI 的输出路径与输入流程。

### 2.2 视觉气质

推荐方向：**现代桌游感 + 清晰工具感**。

- 牌桌：深绿色或墨绿色圆角桌面，强调“游戏空间”。
- 牌面：偏真实麻将牌的白/象牙色，高对比牌字，避免过度拟物导致识别困难。
- 信息面板：半透明深色玻璃卡片或浅色卡片均可，但同一版本需统一。
- 动效：轻量、短促、帮助理解来源与结果；避免长动画阻塞操作。
- 密度：桌面端信息完整，移动端优先保留当前操作与手牌，次要信息折叠。

补充要求：

- 第一眼感知应是“牌桌”而不是“后台面板”：中央绿色桌面面积应明显大于侧边信息区。
- 第一视觉焦点应落在“自己手牌 + 当前动作提示”，而不是日志、诊断或配置说明。
- 可允许偏产品化、卡片化表达，但不应把四家玩家退化成普通列表卡片。
- 除诊断态外，任何时刻都不应让事件流、调试信息、JSON 快照占据牌桌主视觉中心。

## 3. 页面范围与角色

### 3.1 Lobby

**核心目标**：让用户快速开始一局，并理解本局配置。

必须包含：

- 新建对局入口：默认一名人类玩家 + AI 对手。
- 对局配置摘要：玩家数、AI 类型、规则集、起始分。
- 最近对局入口：可选；若未实现，应保留空状态文案。
- 诊断入口：进入最近日志/自检结果，便于开发验收。

交互要求：

- 点击“开始对局”后进入 busy 状态，按钮显示“创建中...”。
- 创建失败时保留当前配置并展示重试按钮。
- 配置未开放编辑时，明确标注“当前版本固定配置”。

### 3.2 Table

**核心目标**：让用户稳定理解局势并完成操作。

必须包含：

- 中央牌桌区：展示牌山余量、最近弃牌、当前轮次、当前行动玩家。
- 四方座位区：展示玩家名、风位/座位、分数、手牌数量、已公开副露、最近动作。
- 自己手牌区：底部固定，支持选牌、出牌、可操作提示。
- 操作区：出牌、吃、碰、杠、胡、过、确认/取消。
- 事件流：展示最近 5-8 条局内事件。
- 诊断入口：展示状态快照、动作日志、错误上下文。

推荐补充：

- 庄家/当前圈风信息应在桌面中心区或顶部状态栏可见。
- 弃牌区应优先采用接近真实牌河的栅格排布，而不是单行文字流。
- 自己刚摸到的牌应在手牌末位或与其他手牌有轻微间距区隔，帮助用户建立摸打节奏。
- 副露区应按吃/碰/杠分组，并与暗手形成稳定视觉边界。

### 3.3 ResultModal

**核心目标**：让用户看懂为什么结束、谁赢了、分数怎么变。

必须包含：

- 结果标题：自摸、荣和、流局、异常终止。
- 赢家/点炮者：若存在点炮，明确标记来源。
- 胡牌原因：胡牌牌型、番种/分值来源、触发牌。
- 分数变化：每名玩家本局变化与累计分。
- 操作入口：再来一局、回到大厅、查看复盘。

推荐补充：

- 结果头图区分“胡牌成功 / 流局 / 异常终止”三种不同情绪语气与图形。
- 若为荣和，需同时突出“胡牌者”与“点炮者”；若为自摸，应明确三家共同支付关系。
- 结果弹窗默认先回答“发生了什么”，再展开“为什么会这样”，最后才给后续操作按钮。

## 4. 桌面布局规范

### 4.1 断点

| 断点 | 宽度 | 布局策略 |
| --- | --- | --- |
| Desktop-L | ≥ 1280px | 完整四方牌桌 + 右侧信息栏 |
| Desktop-M | 1024-1279px | 完整牌桌 + 可折叠信息栏 |
| Tablet | 768-1023px | 压缩座位信息 + 底部操作优先 |
| Mobile | < 768px | 纵向布局，保留自己手牌和操作区，其他信息折叠 |

### 4.2 桌面端空间比例

推荐画布比例：

- 顶部状态栏：8%-10% 高度。
- 中央牌桌：54%-62% 高度。
- 自己手牌与操作区：24%-30% 高度。
- 右侧信息栏：280-360px 宽度，展示事件流、诊断摘要、规则提示。

四方座位层级：

- 自己：底部最大，手牌可读，操作按钮贴近。
- 对家：顶部中等，突出最近动作与弃牌。
- 左/右家：两侧压缩，突出名称、分数、手牌数、副露。
- 当前行动玩家：座位外圈高亮，附加呼吸光或短促描边动画。

牌桌中心建议进一步分层：

- 中心最上层：当前动作提示，如“轮到你出牌”“AI-2 可被碰/胡响应中”。
- 中心中层：牌山余量、圈风/局数、最近 1 条关键动作。
- 中心下层：公共弃牌河或最近响应关联提示。

禁止模式：

- 禁止将四家玩家都放进右侧列表，仅在中央放一个空桌面背景。
- 禁止把主要操作区放到远离手牌的位置，导致“看底部、点侧边、再回到底部”的来回跳视。
- 禁止右侧信息栏宽于自己手牌区的有效阅读宽度，避免产品重心偏成“信息后台”。

### 4.3 移动端布局

移动端必须牺牲“全量同时可见”，但不能牺牲“当前可操作性”：

1. 顶部：局势摘要，包含当前玩家、牌山余量、最近动作。
2. 中部：牌桌简化区，显示弃牌区与其他玩家状态。
3. 底部：自己手牌固定吸底，操作按钮紧贴手牌上方。
4. 抽屉：事件流、完整玩家信息、诊断日志进入底部抽屉或右滑面板。

移动端底部安全区：

- 操作按钮需避开系统 Home Indicator。
- 手牌横向滚动时必须保留选中态，不因滚动丢失。
- 不建议依赖 hover；所有提示必须能通过点击/长按触发。
- 单个主要操作按钮可点击高度建议不低于 44px，横向间距建议不小于 8px。
- 若操作按钮超过一行，优先保证“胡 / 杠 / 碰 / 吃 / 过”语义顺序稳定，不因换行打乱优先级。
- 避免底部多层 sticky 叠压（手牌区/动作区/反馈区同时粘底）；优先只保留动作区粘底，其余信息进入抽屉或随内容流动。

## 5. 视觉规格

### 5.1 牌桌

| 元素 | 桌面建议 | 移动建议 |
| --- | --- | --- |
| 牌桌圆角 | 28-40px | 20-28px |
| 桌面内边距 | 24-32px | 12-16px |
| 中央状态牌 | 180-260px 宽 | 140-180px 宽 |
| 当前玩家高亮 | 2-3px 描边 + 轻阴影 | 2px 描边 |
| 牌河行列 | 6x3 或 7x3 视觉栅格 | 4x2 到 5x2 简化栅格 |

牌桌结构建议：

- 桌面中心应保留可一眼识别的“公共区域”，承载牌山、牌河、最近动作和圈风信息。
- 四家弃牌最好朝向桌面中心组织，而不是全部朝同一方向平铺。
- 玩家座位卡片与牌桌边缘之间需留出稳定留白，避免“信息贴边堆满”导致桌游感消失。

### 5.2 牌面

| 牌面类型 | 桌面尺寸 | 移动尺寸 | 说明 |
| --- | --- | --- | --- |
| 自己手牌 | 44x64 到 52x76px | 34x50 到 42x60px | 最高识别优先级 |
| 他人暗牌 | 24x38 到 32x48px | 18x30 到 24x38px | 只表达数量 |
| 弃牌/牌河 | 28x40 到 34x48px | 22x32 到 28x40px | 支持来源标记 |
| 副露牌 | 32x46 到 40x56px | 24x36 到 32x44px | 需分组展示 |

牌面状态：

- 默认：象牙白底、深色牌字。
- 正式态：优先使用资产化牌面（牌体结构 + 花色语义），文字牌仅作为调试/占位/降级态显示。
- 可出：轻微上浮或底部亮线。
- 已选：上浮 8-12px，增加主色描边。
- 不可出：降低不透明度到 45%-60%，不可仅靠颜色表达。
- 刚摸牌：短促入场动画，持续 160-240ms。
- 最近打出：牌河中附加来源角标与 1.5-2 秒高亮。
- 可胡/可杠等强动作出现时，对应触发牌可同步高亮，但不能遮挡牌面文字。

牌面与牌河细节：

- 弃牌河应保留明显的横纵秩序，避免散乱堆叠成“贴图墙”。
- 最近一张弃牌与历史弃牌要有层级差异，但不能夸张到破坏整体牌河秩序。
- 副露牌需保持组内靠近、组间留白，杠牌应能看出四张关系。
- 若采用极简图形牌面，仍应保证万/筒/条/字牌在 1 米外桌面视距下可快速区分。

### 5.3 色彩语义

| 语义 | 推荐色 | 使用范围 |
| --- | --- | --- |
| 主行动 | 金色/琥珀色 | 出牌、确认、当前行动提示 |
| 安全/完成 | 绿色 | 操作成功、结算正收益 |
| 警告/可响应 | 橙色 | 可吃碰杠胡、倒计时临近 |
| 危险/错误 | 红色 | 失败、断线、非法操作 |
| 信息/诊断 | 蓝色 | 日志、状态快照、复盘入口 |
| 中性 | 灰色 | 次要文本、不可操作状态 |

颜色不得成为唯一信息来源；按钮、标签、图标、文案需共同表达状态。

## 6. 交互状态设计

### 6.1 全局状态机

```mermaid
stateDiagram-v2
    [*] --> LobbyIdle
    LobbyIdle --> CreatingGame: 点击开始
    CreatingGame --> TableLoading: 创建成功
    CreatingGame --> LobbyError: 创建失败
    LobbyError --> CreatingGame: 重试
    TableLoading --> WaitingAI: 进入牌桌
    WaitingAI --> PlayerTurn: 轮到用户
    WaitingAI --> ResponseWindow: 他人弃牌可响应
    PlayerTurn --> SubmittingAction: 出牌/杠/胡
    ResponseWindow --> SubmittingAction: 吃/碰/杠/胡/过
    SubmittingAction --> WaitingAI: 提交成功
    SubmittingAction --> ActionError: 提交失败
    ActionError --> PlayerTurn: 返回可操作
    WaitingAI --> RoundEnded: 胡牌/流局
    PlayerTurn --> RoundEnded: 自摸/结束
    ResponseWindow --> RoundEnded: 荣和/结束
    RoundEnded --> ResultModal
    ResultModal --> CreatingGame: 再来一局
    ResultModal --> LobbyIdle: 回到大厅
```

### 6.2 状态清单

| 状态 | 用户看到 | 用户可做 | 禁止事项 |
| --- | --- | --- | --- |
| LobbyIdle | 开始入口、配置摘要 | 开始对局、查看诊断 | 不展示未生效配置为可编辑 |
| CreatingGame | 创建中按钮、骨架屏 | 取消或等待 | 不允许重复创建多局 |
| TableLoading | 牌桌骨架、加载文案 | 等待 | 不展示半初始化手牌 |
| WaitingAI | 当前 AI 思考中、座位高亮 | 查看日志/复盘入口 | 不允许用户提前出牌 |
| PlayerTurn | 自己手牌高亮、可出牌提示 | 选牌、出牌、可用特殊操作 | 不允许前端自行判断非法牌可出 |
| ResponseWindow | 弃牌来源、响应原因、倒计时 | 吃/碰/杠/胡/过 | 不隐藏“过” |
| SubmittingAction | 操作按钮 loading | 等待、取消仅在接口支持时开放 | 不允许连续提交相同动作 |
| ActionError | 错误原因、重试/返回 | 重试、重新选择、查看诊断 | 不吞错误、不只写 console |
| RoundEnded | 牌桌锁定、进入结算 | 查看结果 | 不允许继续操作手牌 |
| ResultModal | 胡牌/流局原因、分数变化 | 再来一局、回大厅、复盘 | 不只显示胜负，不解释分数 |

### 6.3 倒计时与忙碌态

- AI 思考超过 600ms：显示“AI 思考中...”。
- 动作提交超过 800ms：按钮进入 loading，其他互斥操作禁用。
- 响应窗口剩余 5 秒：倒计时变为警告样式。
- 操作失败：toast + 操作区内联错误同时出现；toast 自动消失，内联错误保留到下一次有效操作。
- 断线/状态同步失败：桌面顶部展示全局错误条，提供重试与诊断入口。

## 7. 用户局势理解设计

### 7.1 最近动作

必须在牌桌中央或右侧事件流展示最近动作：

格式建议：

- `东家 AI-1 打出 三万`
- `你 碰了 AI-2 的 六筒`
- `AI-3 杠 九条，摸补牌`
- `你 胡牌：平胡 + 自摸`

最近动作视觉要求：

- 最近 1 条在牌桌中央短暂强化，1.5-2 秒后降级进入事件流。
- 弃牌应标记来源玩家。
- 响应动作应连接“被响应的牌”和“响应玩家”，可用箭头/连线/同色标签。
- 最近动作文本长度应限制在一行主句 + 一行补充内，避免变成滚动日志。

弃牌河显示建议：

- 每名玩家的弃牌应能按自己的方向归属识别，至少做到“看位置就知道是谁打的”。
- 发生吃/碰/杠时，被响应的那张牌应短暂保留关联高亮，帮助用户追踪牌路。
- 若移动端空间不足，可只强化最近 1-2 张关键弃牌，但不能完全失去来源线索。

### 7.2 响应原因

当出现吃/碰/杠/胡时，操作区不只给按钮，还要解释原因：

- 吃：`可吃：四万 + 五万 + 六万`
- 碰：`可碰：你已有两张 六筒`
- 杠：`可杠：四张 九条`
- 胡：`可胡：满足 平胡，预计 +8`

若核心状态暂未提供完整原因，前端应展示保守文案：

- `核心规则判定可胡，详情见诊断`

禁止前端为了展示原因而重写完整规则判断；原因字段应作为后端/适配层输出的一部分逐步补齐。

### 7.3 分数变化

分数展示分三层：

1. 座位卡片：当前总分。
2. 事件流：本次动作带来的即时分数变化。
3. 结算弹窗：完整本局分数表。

ResultModal 分数表字段：

| 玩家 | 本局变化 | 总分 | 角色 | 原因 |
| --- | --- | --- | --- | --- |
| 你 | +24 | 124 | 赢家 | 自摸 / 平胡 |
| AI-1 | -8 | 92 | 放分 | 自摸支付 |
| AI-2 | -8 | 96 | 放分 | 自摸支付 |
| AI-3 | -8 | 88 | 放分 | 自摸支付 |

### 7.4 可操作提示

操作区必须回答三个问题：

- **现在轮到谁？** 例如：`轮到你出牌`、`等待 AI-2 出牌`。
- **我能做什么？** 例如：`请选择一张手牌打出`、`你可以碰/胡，也可以过`。
- **为什么？** 例如：`AI-1 刚打出 六筒，你已有两张 六筒`。

操作按钮顺序建议：

- 自己回合：`出牌/确认` 为主按钮，取消选牌为次按钮。
- 响应窗口：建议按 `胡 > 杠 > 碰 > 吃 > 过` 的优先顺序组织。
- `过` 必须稳定出现在同一位置，不应因为可用动作数量变化而频繁跳位。
- 默认态应只保留一个强主动作（例如“出牌”或本次主响应动作）；其余动作进入“更多动作”或二级区域，避免长期并列多主按钮。

## 8. 诊断与复盘入口

### 8.1 诊断面板

入口位置：

- 桌面端：右侧信息栏底部固定“诊断”按钮。
- 移动端：顶部更多菜单或底部抽屉入口。
- ResultModal：显示“查看复盘/诊断”。

诊断面板内容：

- 当前状态快照：roundId、turnIndex、currentPlayer、phase、wallCount。
- 最近动作日志：最近 20 条 action/event。
- 前端渲染摘要：选中牌、可用动作、禁用原因。
- 错误上下文：请求参数、响应错误码、可重试建议。
- 导出入口：复制 JSON / 下载日志。若未实现下载，至少支持复制。

约束：

- 诊断入口应“随手可达，但默认弱化”，不能压过主操作区。
- 桌面端建议默认折叠事件流/诊断详情，仅保留轻量入口与最近事件摘要；展开后再展示完整面板。
- 默认态优先展示产品信息；诊断信息属于二级入口，不应抢占首屏牌桌空间。

### 8.2 复盘视图

复盘入口应在 ResultModal 中开放，MVP 阶段可先实现为只读时间线。

复盘最小能力：

- 按时间线展示摸牌、出牌、吃碰杠胡、分数变化。
- 支持跳到关键节点：首次响应、胡牌、错误、流局。
- 支持从某一事件查看当时四家状态摘要。

非目标：

- 不要求 MVP 阶段支持任意回滚重放。
- 不要求用户从复盘中恢复对局。
- 不要求复盘推演 AI 决策依据，除非策略层已提供解释字段。

## 9. 组件设计建议

### 9.1 组件边界

| 组件 | 职责 | 不应承担 |
| --- | --- | --- |
| `LobbyPage` | 创建对局、展示配置与入口 | 麻将规则判断 |
| `TablePage` | 组织牌桌布局、订阅状态 | 直接计算胡牌 |
| `SeatView` | 展示玩家座位、分数、副露、动作 | 修改玩家状态 |
| `TileView` | 展示单张牌与交互状态 | 判断牌是否合法 |
| `HandView` | 手牌选择、排序、出牌触发 | 推导可响应动作 |
| `ActionBar` | 展示可用动作与原因 | 自行构造核心动作 |
| `EventTimeline` | 展示动作流和分数变化 | 替代日志系统 |
| `ResultModal` | 展示结算与后续入口 | 重新结算分数 |
| `DiagnosticsPanel` | 展示状态与错误上下文 | 修改核心状态 |

### 9.2 状态字段建议

Web UI 适配层建议输出一个只读视图模型：

```ts
interface MajiangTableViewModel {
  gameId: string;
  phase: 'loading' | 'waiting_ai' | 'player_turn' | 'response_window' | 'submitting' | 'ended' | 'error';
  currentPlayerId?: string;
  wallCount: number;
  seats: SeatViewModel[];
  selfHand: TileViewModel[];
  discardRiver: DiscardViewModel[];
  availableActions: ActionViewModel[];
  latestEvent?: GameEventViewModel;
  eventTimeline: GameEventViewModel[];
  scoreDelta?: ScoreDeltaViewModel[];
  diagnostics: DiagnosticsSummaryViewModel;
}
```

要求：

- 视图模型由适配层聚合，组件只消费，不反向修改。
- 可用动作必须带 `disabledReason` 或 `reasonText`。
- 错误状态必须带 `recoverable` 与 `retryAction` 描述。
- 结算信息必须来自核心结算结果，不允许前端重新计算。

## 10. 可访问性与易用性

- 所有按钮需有可读文本，不仅依赖图标。
- 牌面需提供 aria-label，例如 `三万`、`东风`、`红中`。
- 当前选中牌需同时通过位置、描边、文本/提示表达。
- 键盘操作建议：方向键移动选牌，Enter 出牌，Esc 取消，数字键选择动作。
- 色弱可读：红/绿收益亏损需配合 `+` / `-`、箭头或文字。
- 动效需尊重系统减少动态效果设置。
- 触屏态下，手牌选中与出牌建议采用“两段式确认”或“选中后主按钮确认”，降低误触弃牌风险。
- 需要长按的信息必须有等价的点击展开入口，避免把长按作为唯一学习路径。

## 11. 阶段B实现一致性验收矩阵

| 场景 | 验收点 |
| --- | --- |
| 创建对局 | Lobby 展示 busy，成功进入 Table，失败可重试 |
| 等待 AI | 当前 AI 座位高亮，用户操作禁用，事件流不丢失 |
| 用户出牌 | 可选手牌有明确选中态，提交后进入 loading，成功更新牌河 |
| 可响应 | 展示弃牌来源、响应按钮、响应原因、倒计时和“过” |
| 非法操作 | 不崩溃，展示错误原因，可回到上一可操作状态 |
| 胡牌结束 | ResultModal 展示赢家、胡牌原因、分数变化、再来一局 |
| 流局结束 | ResultModal 明确流局原因与分数处理 |
| 移动端 | 手牌和操作区可用，事件流可通过抽屉查看 |
| 诊断入口 | 能查看当前状态、最近动作、错误上下文 |
| CLI 保护 | Web UI 改造不改变现有 CLI 测试与路径 |
| 牌桌心智 | 用户能在 3 秒内指出自己位置、当前行动玩家、最近弃牌来源 |
| 牌河可读 | 用户能不依赖日志，仅通过桌面主视图判断最近关键牌路 |
| 操作稳定性 | `过`、主操作按钮、当前选中牌位置在多轮交互中不跳位 |

> 说明：本章属于**阶段B实现一致性验收**，默认要求实现证据（截图、录屏、DOM/状态）支撑。

## 13. 分阶段冲顶审核版

本章节明确区分两层审核口径：

- **普通合格麻将 UI（基线合规）**
- **最顶级麻将 UI（冲顶合规）**

并明确：**基线通过 ≠ 顶级通过**。后续编码和审核不得混判。

### 13.0 阶段定义与证据边界

- **阶段A：设计冻结验收（无代码实现）**
  - 仅审核设计表达与可实现性闭环，不要求实现落地。
  - 可接受证据：Figma/Pencil、线框图、高保真图、交互流图、状态图。
  - 禁止要求：实现截图、DOM 节点、运行态脚本结果、实际交互录屏证据。
- **阶段B：实现一致性验收（有代码实现）**
  - 审核实现是否对齐阶段A冻结稿。
  - 必交证据：桌面/移动截图、关键交互录屏、`tsumo/ron/draw/abort` 四结果证据、必要 DOM/状态校验。

### 13.1 普通合格麻将 UI（基线合规）

满足以下条件可判“普通合格麻将 UI”：

- 四方牌桌结构成立（非列表式堆叠）。
- 自己手牌固定在底部，主操作区贴近手牌。
- 中央能直读最近动作与牌河，不依赖日志区。
- 当前行动玩家与可响应原因可见。
- 结算页可解释“谁赢、为什么、分数怎么变”。

### 13.2 最顶级麻将 UI（冲顶合规）

在满足 `13.1` 的前提下，必须额外满足：

- 桌心第一视觉锚点明确：先看到“谁打了什么牌 -> 我能否响应 -> 当前唯一主路径”。
- 牌面系统采用成熟图案牌/资产化牌面，牌是主语言，不是文本块/按钮块。
- 打牌链路默认只有一个强主动作，用户不需要在多个同级主按钮反复决策。
- 信息密度受控：强桌心、弱侧栏，底部与侧栏不同时抢主视觉。
- 界面整体呈现商业成品感，而非高密度功能原型感。
- 不得以“功能完整 / 文档齐全 / 自动化通过”替代顶级结论。
- 最顶级判定必须同时引用 `13.1 + 13.6 + 14.7 + 13.3/13.4 双否决项复核`，不得仅写单侧否决项。

### 13.3 设计否决项（阶段A）

以下任一项命中，阶段A不得通过：

1. 设计稿无法表达“谁打了什么牌 -> 我能否响应 -> 当前主路径”。
2. 牌面系统未定义正式态（仅有文字牌描述，且未限制为调试/占位/降级态）。
3. `出牌/确认/取消` 在设计稿中长期并列为同级主动作，未给出默认唯一主动作收敛策略。
4. 四方座位、桌心公共区、底部手牌关系不稳定，退化成列表台/日志台表达。
5. 移动端策略缺失（未定义折叠/抽屉与密度收敛）。
6. 结果页信息结构不完整（无法解释赢家、点炮/支付关系、分数变化）。
7. 设计冻结阶段要求提交实现截图、DOM 或运行态脚本结果（流程性否决）。

### 13.4 实现否决项（阶段B）

以下任一项命中，阶段B不得通过：

1. 正式主牌面仍以文字牌为默认主表达（未落实阶段A的牌面系统冻结）。
2. 默认主动作未收敛，`出牌/确认/取消` 长期同级并列。
3. 首屏出现桌心 + 底部 + 侧栏同时高密度抢主视觉。
4. 桌心链路不可直读（无法立即判断“谁打牌 -> 能否响应 -> 主路径动作”）。
5. 结果页四类型（`tsumo/ron/draw/abort`）证据缺失或解释不闭环。
6. 阶段B缺少必交证据（桌面/移动截图、关键交互录屏、必要 DOM/状态校验）。
7. 实现偏离阶段A冻结稿核心视觉与交互口径，且未回流阶段A补冻结。

### 13.5 反例：常见退化方向

- 列表台：四家变资料卡列表，失去牌桌空间关系。
- 日志台：靠事件流理解局势，主视图不可直读关键牌路。
- 按钮台：动作入口多且同级，主路径不明确。
- 诊断台：调试信息抢占首屏视觉中心。
- 原型堆叠台：模块都对但信息层级平均，桌心张力不足。

### 13.6 编码实现时最小正例目标（仅基线，不代表顶级）

若资源有限，编码 agent 至少先做到：

- 明确四方牌桌结构。
- 底部固定手牌区 + 贴手牌操作区。
- 中央最近动作提示 + 牌河。
- 当前行动玩家高亮。
- ResultModal 的胜负原因 + 分数变化。

仅满足上述 5 点，只能判“基线合规”，不能宣称“最顶级 UI”。

## 14. 分阶段审核清单

本清单可直接交给编码 agent、设计修订者或 reviewer 使用。默认要求“逐项确认”，不能只做笼统口头判断。

### 14.0 阶段A设计冻结验收清单（无实现证据）

- [ ] 仅提交设计证据（Figma/Pencil/线框图/高保真图/交互流图/状态图）。
- [ ] 未要求实现截图、DOM 节点、运行态脚本结果。
- [ ] 桌心主路径表达清晰（谁打牌 -> 能否响应 -> 主动作）。
- [ ] 牌面系统定义完整（正式态/降级态边界清楚）。
- [ ] 四方座位、中央公共区、底部手牌空间关系稳定。
- [ ] 移动端密度策略明确（折叠/抽屉/主次层级）。
- [ ] 结果页信息结构完整（赢家、点炮/支付、分数变化）。
- [ ] 阶段A通过结论已形成，才允许进入阶段B开发。

### 14.1 阶段B实现一致性清单（实现证据必交）

- [ ] 已提供桌面端与移动端截图证据。
- [ ] 已提供关键交互录屏证据（至少覆盖出牌/响应/结算）。
- [ ] 已提供 `tsumo/ron/draw/abort` 四类型结果页证据。
- [ ] 已提供必要 DOM/状态校验证据。
- [ ] 实现与阶段A冻结稿一致，未偏离核心视觉与交互口径。
- [ ] 若发现设计缺口，已回流阶段A补冻结，再继续阶段B。

### 14.2 结构清单

- [ ] 自己手牌固定在底部，且是最大可读区。
- [ ] 其他三家围绕桌面分布，不是普通列表。
- [ ] 桌面中心存在公共区域，承载牌河 / 最近动作 / 圈风 / 牌山信息。
- [ ] 主操作区紧贴手牌，不需要跨大区域跳视。
- [ ] 诊断入口存在，但不是主视觉中心。

### 14.3 局势理解清单

- [ ] 用户 3 秒内能判断当前轮到谁。
- [ ] 用户 3 秒内能判断最近是谁打出哪张牌。
- [ ] 用户 3 秒内能判断自己现在能做什么。
- [ ] 吃/碰/杠/胡出现时，有原因说明，而不是只有按钮。
- [ ] 分数变化既能在过程中追踪，也能在结算中复盘。

### 14.4 交互清单

- [ ] 选牌态、出牌态、响应态、提交中、失败态都存在明确反馈。
- [ ] `过` 始终可见且位置稳定。
- [ ] 响应动作顺序不乱跳，保持稳定优先级。
- [ ] 移动端点击热区足够，不依赖 hover。
- [ ] 误触风险可控，尤其是出牌与响应确认。

### 14.5 视觉清单

- [ ] 第一眼更像牌桌，而不是后台管理台。
- [ ] 牌河有秩序，能看出来源与近期重点。
- [ ] 副露区有分组，不与手牌混淆。
- [ ] 色彩表达有语义，但不依赖颜色作为唯一信号。
- [ ] 当前高亮、最近弃牌、可响应牌之间层级分明。

### 14.6 边界清单

- [ ] 前端没有重写胡牌/吃碰杠规则，只消费核心层结果。
- [ ] 视图模型承担聚合职责，组件只负责展示与交互。
- [ ] Web UI 改动不影响 CLI 路径与既有测试语义。

### 14.7 顶级档专项清单（冲顶硬标准）

以下为“最顶级麻将 UI”专项硬标准，需逐条勾选：

- [ ] **图案牌面硬标准**：正式态主牌面使用图案牌/牌面资产系统；文字牌仅用于调试/占位/降级态。
- [ ] **唯一主动作硬标准**：默认只有一个强主动作；`确认/取消` 仅在条件性场景出现，不长期并列为同级主按钮。
- [ ] **主路径可直读硬标准**：用户第一眼可识别“谁打牌、目标牌、我该执行哪个主动作”。
- [ ] **去堆叠硬标准**：不存在桌心外信息区（侧栏+底部）同时高密度抢主视觉。
- [ ] **强桌心硬标准**：桌心为第一视觉锚点，侧栏是补充区，不反向主导注意力。
- [ ] **成品感硬标准**：整体观感不应停留在“高质量原型”；需具备商业成品级完成度。
- [ ] **非替代性硬标准**：不能把“功能完整 / 文档齐全 / 自动化通过”误判为顶级通过。
- [ ] **否决项复核**：`13.3`（阶段A）与 `13.4`（阶段B）否决项必须全部未命中。

### 14.8 冲顶快检（审核执行版）

以下条目用于 reviewer 的“是/否”快速判定，任一否决项命中即直接不通过：

- [ ] 正式主牌面是图案牌面（非文字牌面默认主表达）。
- [ ] 默认不存在 `出牌/确认/取消` 长期同级并列。
- [ ] 用户第一眼可识别唯一主动作（不需要二次猜测）。
- [ ] 首屏未出现桌心 + 底部 + 侧栏同时高密度抢主视觉。
- [ ] 第一眼能锁定“谁打了什么牌 -> 我能否响应 -> 当前主路径”。
- [ ] 未把“功能完整 / 文档齐全 / 自动化通过”当作顶级通过依据。
- [ ] 未命中 `13.3` 任一否决项。

## 15. 是否可直接交给编码 agent（分级表述）

### 15.1 阶段切换闸门（必须）

- 必须先通过阶段A设计冻结验收，再进入阶段B开发与实现验收。
- 阶段B如出现设计缺口，必须回流阶段A补冻结，禁止绕过冻结稿直接改实现口径。

### 15.2 可直接做基线实现（可以）

可以直接交给编码 agent 做“普通合格麻将 UI（基线合规）”实现与迭代，前提是：

- 满足 `13.1` 与 `13.6`。
- 满足 `14.0`（阶段A通过）与 `14.1~14.6`（阶段B执行清单）。
- 严守边界：不重写核心规则，不影响 CLI 路径。

### 15.3 不可宣称顶级成品（除非满足冲顶专项清单）

未经 `14.7` 全部通过，且 `13.3`（阶段A）与 `13.4`（阶段B）否决项全部未命中时：

- 不得宣称“最顶级麻将 UI”。
- 不得以“功能完整 / 自动化通过 / 文档齐全”替代冲顶结论。
- 只能表述为“基线合规”或“冲顶进行中”。
- 无外部样本对照证据时，仅可写“冲顶进行中”或“冲顶暂定”。
- 顶级判定必须同时引用 `13.1 + 13.6 + 14.7 + 13.3/13.4 双否决项复核`，不得仅写单侧否决项。

### 15.4 对编码 agent 的执行要求

- 先满足 `13.6`（基线），再进入 `14.7`（冲顶）。
- 每次改动后先跑清单，不允许只写“更高级/更沉浸”等形容词结论。
- 若视觉强化与局势可读性冲突，优先保留局势可读性。

## 16. 非目标与边界

- 不在 Web UI 中重新实现胡牌/吃碰杠规则。
- 不在本阶段重构 CLI。
- 不要求 MVP 阶段实现联机多人。
- 不要求 MVP 阶段实现完整 AI 决策解释。
- 不要求前端独立保存可恢复对局，除非核心层提供稳定序列化能力。

- 依据 `docs/majiang/FOLDER_STRUCTURE.md`：Web UI 仍属于 UI 层职责，只负责渲染游戏状态和处理用户输入。

- 当前未发现规范冲突；若后续具体实现与 CLI 或核心规则产生冲突，应优先保护核心规则与 CLI 既有行为。
